# Alive2 能否执行 eBPF 机器码

结论是有条件可行。符号执行器、CFG、phi 和有界循环展开可以不经过 LLVM 前端使用。本轮只验证了算术、比较、跳转和一条 alloca 内存路径。eBPF 内存指令、helper、Map 和 RV32IMC 还没有做。

目录是 `classifier/alive2/`。它是 classifier 仓库里的普通目录，不是 git submodule。上游源码在 `third_party/alive2/`，没有 `.git`，因此 `git add` 会把它记成普通文件。上游 commit 是 `adacbd5180ccf95075e9867c4f0c259f59c9fef2`。ISA 对照的是 Linux v6.12 的 `Documentation/bpf/standardization/instruction-set.rst`。

## 已经跑通的部分

Alive2 在这台机器上以 `BUILD_TV` 关闭的方式编过。链接的是 `ir`、`smt`、`tools` 和 `util`，没有 LLVM。Clang 23 的 libc++ 要求显式包含 `<iterator>`。这个修改只在五个源文件里，补丁是 `patches/clang-iterator.patch`，不改变指令语义。

直接构造 Alive2 IR 的程序是 `build/direct_ir`。日志是 `direct-ir.log`。

`x + y * 3` 的返回表达式是 `(bvadd x (bvmul #x00000003 y))`。对全部 32 位输入，包括 `x = 0xffffffff`、`y = 1` 得到 2 的回绕，求解结果是 UNSAT。把参考式换成 `x + y * 4` 得到 SAT，所以这个检查不是恒真。

`x > 10` 经过 phi 合并后的返回表达式是 `(ite (bvule #x0000000b x) (bvadd x #x00000001) (bvadd x #xffffffff))`。它和 `ite(x > 10, x + 1, x - 1)` 的不等价查询是 UNSAT。对调两个分支得到 SAT。

一条 `alloca`、`store`、`load` 把符号输入原样读回。定义性查询在输入不是 undef 也不是 poison 时是 UNSAT。内存摘要里能看到按小端写入的四个字节。

eBPF 机器码程序是 `build/ebpf_test`。日志是 `ebpf-test.log`，退出码 0。

解码按小端读取 8 字节指令。规范例子 `07 01 00 00 44 33 22 11` 解成 `alu64 add r1, 0x11223344`。不认识的 opcode 会报错。`LDX` 被拒绝，没有当成空操作。

`clang -target bpf` 对 `(unsigned)(x + 1)` 的机器码是 `bf 10 00 00 00 00 00 00`、`04 00 00 00 01 00 00 00`、`95 00 00 00 00 00 00 00`。测试断言这些字节和前端里的 ALU32 程序相同，再做符号等价。这只是一条端到端字节对照，不代替 ISA 参考模型。

## 哪些语义可以直接映射

`ebpf-test.log` 里单独有用例的位运算是 64 位 `AND`、`OR`、`XOR`。单独有用例的比较是 `JNE`、`JLT`、`JLE`、`JGE`、`JSGE`、`JSLT`、`JSLE`，以及它们的 `JMP32` 形式。`JEQ`、`JA`、`JGT`、`JSGT`、`EXIT`、加减乘、`MOV` 和 `NEG` 出现在其他程序里，没有各自的一行用例。`JMP32` 的 `JEQ`、`JGT`、`JSGT` 没有单独用例。

`JMP32 JNE` 用 `r1 = 0x100000000` 和立即数 0 比较。低 32 位相等，所以不跳。按 64 位比较则会跳。把 `JMP32` 比较改成 64 位操作数后，这条等价查询是 SAT。`jge32 trunc` 的具体点 `0x1ffffffff >= 1` 在 32 位和 64 位下都为真，单靠这个点分不开宽度。它的全输入等价查询在宽度被改错时是 SAT。

条件跳转变成 Alive2 的 `icmp` 加 `br`，汇合点用 phi。

下面几项不能把同名 LLVM 运算直接拿来用。测试覆盖了它们。

ALU32 先截断到 32 位，运算后再零扩展回 64 位。`r1 = 0x1ffffffff` 再做 ALU32 加 1，结果是 0。把它错做成 ALU64 时，等价检查是 SAT。

ALU64 的 32 位立即数做符号扩展。无符号 `DIV` 的立即数也先符号扩展，再按无符号数使用。`2^32 / -1` 的结果是 0，因为除数是 64 位全 1，不是 `0xffffffff`。

无符号 `DIV` 在除数为 0 时结果是 0。无符号 `MOD` 在除数为 0 时，ALU64 保留原目标寄存器，ALU32 把高 32 位清零。实现上先分支，只有除数非 0 的块里才放 `udiv` 或 `urem`。Alive2 的 `udiv` 本身会把除零记成 UB。若直接使用它，等价检查是 SAT。分支之后，除零输入上的定义性查询是 UNSAT。

移位先和 `31` 或 `63` 做与，再做 `shl`、`lshr` 或 `ashr`。`1 << 127` 得到 `1 << 63`。算术右移和逻辑右移在 `0x8000000000000000` 上结果不同。有符号 `JSGT` 把 `-1 > 0` 判为假，无符号 `JGT` 判为真。

## 控制流和循环复用了什么

基本块、边、phi 和 `Function::unroll` 都是 Alive2 原有的。前端没有自己展开机器码。

循环程序是 `r0` 从 0 开始，每次加 1，`r1` 减 1，直到 `r1` 为 0。`unroll(1)` 对行程 0 和 1 给出返回值，返回表达式是 `(ite (= r1 0) 0 1)`。`unroll(4)` 覆盖行程 0 到 4。行程 5 到 8 没有返回。展开后的回边指向 `#sink`，不指向下一次迭代。返回条件里同时要求输入不是 undef、不是 poison，并且行程落在展开范围内。未覆盖的行程没有被记成已验证。

这个展开次数和 Alive2 的 `k` 不是同一个数。测到的事实是 `unroll(1)` 覆盖两个行程，`unroll(4)` 覆盖五个行程。多出来的一次来自 Alive2 为循环出口多复制的头块。还没有证明这个差对所有循环形状都成立。

## 还没有验证的部分

没有实现有符号除法和取模、`MOVSX`、字节交换、内存指令、`CALL` 和 64 位立即数宽指令。未实现的 opcode 会报错。

eBPF 的栈、包和 Map 还没有接到 Alive2 的内存模型上。现在只知道一条 `alloca` 能往返。Alive2 的内存带有块号、来源和 poison 字节。默认的块数量会把纯算术程序的定义性条件撑得很大。纯算术测试把本地块和非本地块数量设成 0 之后，定义性条件只剩下输入不是 undef、不是 poison。这是调用约定，不是 eBPF 内存语义。

寄存器的初始模型有一个假设。测试标明的寄存器是符号输入，其余寄存器从 0 开始。这不是 Linux 验证器对未初始化寄存器的结论。

RV32IMC 对照、可观察事件和 helper 都没有做。

## 结构上会挡住完整 ISA 的地方

除法和超范围移位在 Alive2 里是 UB 或 poison。eBPF 把这两类情况定义成回绕、掩码或除零结果。每条这样的指令都要在前端里改写成分支或掩码，不能靠同名运算。这个成本是局部的，现有测试已经覆盖了无符号除法和移位。

如果 eBPF 内存或 helper 不能用现有的 load、store 和显式边界条件表达，就要改 Alive2 的内存模型或执行状态。那一步超出了这次前端适配，还没有实验证据。

有界展开可以复用，但不能把它的返回域说成整个程序的证明。超出 `#sink` 的路径必须继续标成未覆盖。
