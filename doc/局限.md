# 局限

匹配失败是分析没有确认，不是编译错误。验证器也会拒绝一对观察含义已经一致的程序。下面三件事，当前规则不处理，或者只处理其中一部分。

## 观察错位

Clang 会按目标调整指令调度和分支结构。局部重新配对只覆盖连续的 PacketWrite 或 MapWrite，并且不跨过 Branch、Return、helper 或节点边界。分支条件的次序变化不在这个范围里。

`just_tx` 检查 `h_proto` 是否等于小端常数 129 或 43144。eBPF 先看 129，RV32 先看 43144。保序配对会把 \(\neq 43144\) 和 \(\neq 129\)、\(=129\) 和 \(=43144\) 配在一起。表达式匹配不把这两个常数看成同一个值。只把 Branch 当成无序的一组，也还要同时接上条件的组合和后继。当前的局部双射不做这件事，所以这个程序保持弱匹配。

## 符号比较

包长度检查说明：字面结构不同的两式，要在额外的整数前提下才可能同时成立。设包起点和包终点都能用同一个 32 位无符号值 \(x,y\) 表示，\(+_w,-_w\) 是模 \(2^w\) 的加减。一端写下 \(y<x+_{32}32\)，另一端写下 \(y-_{32}(x+_{32}8)<24\)。若再假设 \(x+32<2^{32}\)，这两组关系可以同时成立或同时不成立。\(x+32<2^{32}\) 不能从已有的包界约束里推出来。

当前的表达式匹配没有做这个联合推理。它也不把不等式两边同时减去一项再和 0 比较：对无符号的 `gtu` 或 `leu`，\((a-b)\mathrel{\mathrm{gtu}}0\) 只表示 \(a\neq b\)。

已经做的是另一件事。提到包尾的 Branch，在「32 位地址相加不从第 31 位进位」的假设下读成同一个标记。载荷上的 `add` 和 `mullo` 只有在结果确知小于 \(2^{32}\) 时才收成 32 位。`*N32` 只说明低 32 位的比较，不说明两个 64 位值相等。这些读法使 `incr`、`square`、`bitswap`、`bsort`、`firewall` 和 `merge_try` 的相应分支在测量中成为严格匹配。它们不是上面那个整数前提的证明，也没有把任意 64 位运算收成 32 位运算。

## 循环

一端用指针和包终点比较，另一端用计数器和上界比较时，只看最后一次分支不够。还要联系初值、更新、退出条件，以及每一轮写入的偏移、值和次数。首轮观察的结构相同，推不出后面各轮仍然相同。

现有方法先匹配路径，再逐对检查参数。它不在循环的各轮之间建立「位移等于计数器」这一类关系。循环区域里不做严格的表达式匹配。含有回边截断的程序对整体至多是弱匹配，因此不进入命题 1 的接受前提。没有选定观察的循环片段，也不能用当前要求非空的观察节点表示。
