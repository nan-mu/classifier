# 匹配

跨架构分析比较两端推演出的观察序列和参数。它分成路径匹配和表达式匹配。Clang 为不同目标调度指令，同类观察的次序可以不同。局部重新配对只处理后文允许的写入重排。

## 路径匹配

路径匹配把有序观察收成节点。单端节点保存非空观察序列，以及 `taken` 和 `not_taken` 两个指针。比较节点成对保留两端的序列和指针。\(K\) 只取 Figure 2 的类别，按序列的原顺序读取，不看参数。

序列最后一项是 Return 时，两个指针都是空。否则，一个后继指向同一个节点，两个后继分别连接。回边可以指回已经有的祖先。父节点末尾和子节点开头若是同一次 Branch，按所沿的边确定方向，拼接时只保留一条 Branch。

路径匹配函数 \(f\) 接收两端的观察图，返回比较图或失败。命题 3 要求节点配对是双射，并且每个比较节点里有一个保序的观察双射 \(\beta_n\)：配成一对的观察类别相同，先后顺序保持，参数可以不同。重复出现的相同观察仍按位置分开算。

**命题 3（路径匹配）** 若 \(f(G_E,G_R)=H\)，则从比较图节点到两端输入图节点的对应都是双射，且每个比较节点上都存在观察出现之间的保序双射，配对双方的类别相同。

这条命题的完整证明还没有完成。类别和顺序一致，不表示操作或资源偏移相同。

实现里的 `pathMatch` 是这条要求在一条观察序列上的检查：两边等长，且按位置的类别相同，然后配成 \((0,0),(1,1),\ldots\)。类别不同或条数不同就是失败。比较图的分叉、回边和出口仍由服务端维护。`matchStatus` 通过只说明类别顺序、分叉形状和出口一致，还不读表达式。

## 表达式匹配

表达式匹配检查同一比较节点里的一对同类观察 \(o,o'\)。循环区域内的参数不调用这个检查。\(\rho\) 是覆盖左侧比较表示里全部符号的有限对应。变元的对应和寄存器的对应各自单射。每一对观察单独建一份对应。

**命题 4（表达式匹配）**

\[
g(o,o')=\mathrm{true}
\Longrightarrow
\exists\rho,\quad \rho(\widehat o)=\widehat{o'}.
\]

\(g\) 为真表示这一对在合法换名之后结构相同。为假表示还没有确认，不表示两端行为不同。这条命题的完整证明还没有完成。

`prepare` 先做 `solve`，再按渲染顺序排列 Branch 的两个操作数。左边渲染更大时，交换操作数并改用 `Rel.swap`。大小比较因此可以换成对侧的关系，有符号、无符号和比较位数保持原样。

`exprMatch` 在 `prepare` 之后还做写法识别，然后才做单射换名。换名要求常数同值，运算符号和位宽相同。变元只能改成同宽度的变元。寄存器要能对应，并且展开事件相同。`unifyLists` 只做 `prepare` 和整表换名，不做下面这些写法识别。引理 3 说的是整表匹配，不自动适用于 `exprMatch`。

## 写法识别

下面几条只作用在 `exprMatch` 看到的 Branch 上。它们把两端已经写下的项读成同一个比较表示。每一条都有前提。前提不成立时，结构相同不表示数值相同。

**包尾。** RV32 把包尾写成 `add32(v32:4,v32:5)`。eBPF 写成 `add32(v32:4,128)`，再套上不改变该值的 `zext`、`low` 和 `id`。一条 Branch 提到其中一种写法时，两端都改用同一个包尾标记，并把相关的 32 位加减按 32 位读取。`leuN32` 这一类低 32 位关系改读成普通的 32 位关系。

假设：参与这个地址加减的值是 32 位的，比较也在 32 位上进行，并且加法不从第 31 位向外进位。这是地址和的读法，不是从包界不等式推导出来的定理。包长变量没有被替换成常数 128。没有提到包尾的 Branch 不使用这条读法。

**载荷。** `zext`、完整宽度的 `low` 和从 0 开始且盖住全部有效位的 `extract`，只在不改变数值时去掉。`add` 和 `mullo` 收到 32 位，仅当静态界说明结果小于 \(2^{32}\)。一个字节乘 \(256\)、\(65536\) 或 \(16777216\) 满足这一点。两个任意的 32 位值相乘不会被收窄。只含包基址 `v32:4` 的按位或被摊平并排序，因为按位或可结合、可交换。出现其他变元的或保持原样，所以 `or32(or32(v32:1,v32:2),v32:3)` 与 `or32(v32:3,or32(v32:1,v32:2))` 仍然对不上。

`*N32` 比较的是低 32 位，所以关系改读成对应的 32 位关系，常数按 \(2^{32}\) 取余。因此 `gtuN32` 一侧的 \(2^{64}-5\) 可以和 32 位一侧的 \(2^{32}-5\) 成为同一个常数。没有 `N32` 的 64 位等式不这样做。`zext8` 作用在任意 32 位变元上时也不去掉，因为那会丢掉高位。

**Helper 返回值。** `externalResult` 的事件是产生这次调用的展开节点号。参数都落在 32 位里时，事件从返回值里去掉，返回值按 32 位读。helper 号、Map 和键字节都保留。

假设：64 位 helper 寄存器的高 32 位为 0，因此和 0 比较的结果与 32 位返回寄存器一致。若某次 helper 的高 32 位可以非零，这条读法会把不同的返回值看成同一个。

## 局部重新配对

初始的保序配对失败，并且失配落在同一节点里连续的 PacketWrite 或 MapWrite 上时，才在这一段里另找双射。这一段在 helper、Branch、Return、另一类写入或序列尽头处停下。段与段不重叠。原序列不改写。段内每一对仍用 `exprMatch` 检查，所以段内的 Branch 不会被拿来重排；若一段写入的参数里含有包尾写法，检查会看到前面的识别。

超过六次写入的段不搜索。包写入要求目标区间互不相交，并且源里能够确认的包读取不与段内其他写入重叠。不能确认的 `packetRead`，或地址不是常数的 `inputByte`，不足以通过这个检查。Map 段还要求 Map 和键是常数，并拒绝源项里再出现 Map 寄存器。找不到这样的双射时，记为参数没有匹配上，不把路径判为错误，也不把程序判为不等价。

`just_tx` 交换 MAC 地址时，RV32 的六个半字偏移是 0、2、4、6、8、10，eBPF 是 0、8、2、10、6、4。保序配对会把不同偏移配在一起。在上面的独立性条件成立时，六次 PacketWrite 可以按偏移和写入项重新配对。

## 严格与弱

路径或回边对不上，结果是失败。路径匹配通过之后，参数、写入独立性或局部双射没有确认，保留为弱匹配。有单轮回边截断的程序对，整体至多是弱匹配，不因为其余观察已经匹配上而升级。只有路径匹配通过、没有循环截断、最终每一对观察都通过表达式匹配，并且局部重排的限制也满足，才是严格匹配。命题 1 只把严格匹配当作 \(\mathrm{true}\)。

profile 的测量比这句话窄：它检查分析是否完成、类别顺序是否一致，以及分支表达式还有多少对没有匹配上。`bitswap`、`bsort`、`firewall`、`incr`、`merge_try`、`square` 在当前规则下是严格匹配。`buf`、`fib`、`fletcher32`、`helper_loop`、`just_tx`、`memcpy` 仍是弱匹配。这是这一组程序、预算 1024 下的测量，不是命题 1 的证明。
