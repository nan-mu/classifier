# 任务：按照现行文档规范完成推理流程，并验证 Web UI 全流程正确运行

## 一、总体目标

本次任务的核心目标是：**使最新文档规范所描述的推理流程真正可运行，并确保 Web UI 能够完整、正确、无错误地执行和展示推理过程。**

最终应达到以下状态：

1. 最新文档定义的推理流程能够在实际代码中正确执行。
2. Web UI 可以正常启动、发起推理、接收结果，并完整展示推理过程。
3. 整个推理过程能够正确执行直至完成，不出现运行错误、协议错误或未处理异常。
4. **Merge 和 Merge-Step 必须得到正确实现和实际使用**，而不只是存在相关接口或代码。
5. Lean 4 的数学定义、实现行为及对应文档始终保持一致。
6. 如果现有实现无法满足最新规范，允许修改、重构或替换旧实现，不必为了兼容旧设计而牺牲正确性。

**最终验收标准是实际可运行的端到端推理流程，而不是代码能够编译、接口能够调用或单元测试能够通过。**

## 二、以现行文档规范为最高依据

开始工作前，请先阅读项目中的最新规范文档，理解当前定义的推理流程、相关数学定义及各个操作的语义。

特别关注：

- Create、Step、History、Merge 之间的关系和完整推理流程。
- Merge 和 Merge-Step 的定义、适用条件及实际执行行为。
- Expr、Predicate、状态以及推理历史的现行定义。
- 推理过程中的分支创建、状态传播、历史复用和节点连接。
- Lean 4 推理接口与后端、Web UI 之间的数据交互。

请自行定位相关文档和实现文件，不要假定旧版文件结构或接口设计仍然有效。

### 规范优先级

**最新且现行有效的文档规范优先于旧版本实现、旧规则、旧限制和历史设计。**

之前版本中的某些规则、限制或实现假设，可能已经与本次任务的目标发生冲突。

遇到冲突时：

1. 以当前有效的规范定义为准。
2. 检查旧规则是否仍有存在的必要。
3. 对于已经失效或与现行规范冲突的限制，可以直接修改或移除。
4. 不要为了满足旧实现而修改现行规范的语义。
5. 不要因为过去某个接口不支持某项操作，就认为该操作不需要实现。
6. 如果规范本身存在真正的歧义或内部矛盾，应结合当前数学定义和推理流程进行分析，不得通过静默降低语义要求来绕过问题。

请特别注意：**任务不是让新规范适配旧代码，而是让整个系统正确实现新规范。**

## 三、可以通过 OMP 委派 Lean 4 任务

当前环境已提供 `omp`（Oh My Pi）CLI。

你可以通过终端调用 OMP，将 Lean 4 相关工作委派给独立 Agent。

OMP 具有自己的模型、上下文、工具及 Skills，可以直接处理项目文件。

### 允许委派的工作

- Lean 4 数学定义及推理语义的分析。
- Lean 4 代码实现、修改和重构。
- Create、Step、History、Merge、Merge-Step 相关逻辑的修复。
- Lean 4 接口和数据结构的调整。
- Lean 4 代码与规范文档的一致性检查。
- Lean 4 相关规范文档的同步更新。
- Lean 4 编译错误、证明错误及运行错误的修复。

调用前可以使用 `omp --help` 确认当前版本支持的命令参数。一次性任务优先使用非交互模式；需要连续迭代时，可以考虑使用 OMP 的会话机制。

### Agent 职责划分

你是本次任务的主 Agent，负责：

- 理解完整项目结构和当前规范。
- 规划整体修改。
- 维护 Lean 4、后端和 Web UI 之间的接口一致性。
- 将合适的 Lean 4 任务委派给 OMP。
- 负责 Web UI 和后端的修改与集成。
- 检查 OMP 的实际修改结果。
- 执行最终端到端验证。

OMP 可以直接修改所委派范围内的代码和文档，但需要明确任务边界，避免两个 Agent 同时修改同一文件。

**不要将 OMP 仅作为问答工具。需要修复 Lean 4 实现时，可以直接要求 OMP 完成代码修改。**

OMP 完成后，请检查文件差异、构建结果及实际运行行为。不能仅凭 OMP 的文字回复认定任务完成。

## 四、Lean 4 实现与文档必须同步

本项目的 Lean 4 文档不仅用于解释代码，还定义了推理系统应该满足的数学语义和运行行为。

因此，在整个修改过程中必须确保：

1. Lean 4 实现遵循当前有效的数学定义。
2. 修改 Lean 4 的实际行为时，同步检查并更新受影响的规范文档。
3. 修改规范中的操作语义时，同步修改对应代码。
4. 不允许出现文档描述一种行为、代码实际执行另一种行为的情况。
5. 不允许为了通过编译或运行验证而临时改变数学语义。
6. 不允许让已经失效的旧文档继续充当有效规范。

文档更新应着重保持数学定义、输入输出、前置条件、状态变化和推理规则的准确性，不要引入与规范无关的大量实现细节。

## 五、重点完成 Merge 与 Merge-Step

Merge 和 Merge-Step 是本次任务的重点验收对象。

请仔细阅读其最新数学定义和流程规范，并检查当前 Lean 4 实现是否满足要求。

尤其需要关注：

- Merge 的触发条件和判定依据。
- Merge 与 History 之间的关系。
- Merge 后推理过程如何继续。
- Merge-Step 在推理流程中的实际职责。
- Merge-Step 与普通 Step 的区别。
- Merge 是否真正参与历史复用，而不是仅生成某种标记。
- Merge 后的节点关系、状态信息和推理历史是否正确。
- Web UI 是否能够准确展示 Merge 和 Merge-Step 的执行结果。

请注意，**Merge 不应被简单地理解为完整机器状态相等，也不应未经规范允许就被实现成状态合成。**

应根据现行规范明确其判定关系，以及未来 Predicate 的数据依赖、控制依赖、可达性和发生顺序等语义要求。历史中已经产生的 Predicate 不能仅因为后续路径被复用而丢失。

具体实现以现行规范为准，不要直接套用旧版本的 Merge 行为。

最终必须通过实际推理验证 Merge 和 Merge-Step 确实执行了正确操作，而不是只确认相关函数被调用。

## 六、完成整个 Web UI 推理流程

请从真实用户使用 Web UI 的角度验证系统。

需要确保：

1. Web UI 可以正常启动并连接后端。
2. 后端能够正常调用 Lean 4 推理能力。
3. Create 能够正确初始化推理。
4. Step 能够正确推进推理并生成需要的后继。
5. History 能够正确记录和提供后续推理需要的信息。
6. Merge 能够在符合条件时正确复用历史推理。
7. Merge-Step 能够正确执行其规定的后续操作。
8. 前端能够准确展示推理节点、分支、节点之间的关系和各节点状态。
9. 推理流程可以持续执行直到完成，不因 Merge、分支或状态传播而陷入错误。
10. 最终显示的推理结果与 Lean 4 的真实执行结果一致。

不要只验证某个孤立模块，也不要以模拟数据代替真实的 Lean 4 推理结果来完成验收。

如果发现 Web UI、后端与 Lean 4 之间存在接口不一致、数据丢失或语义误解，请直接修复相应模块。

## 七、执行方式

请按照以下阶段推进任务。

### 阶段一：理解现行规范与项目结构

阅读最新规范、Lean 4 实现、后端及 Web UI，确定完整调用链和现行推理流程。

识别当前实现与规范之间的实际差异，但不要停留在审查报告阶段。

### 阶段二：修复推理核心

优先保证 Lean 4 推理语义正确。

如果核心实现不满足规范，可以通过 OMP 委派修复，并检查其修改结果。

对受影响的 Lean 4 文档同步维护。

### 阶段三：完成系统集成

根据修复后的推理能力，调整后端接口、数据转换、状态管理和 Web UI。

确保推理过程中所需的信息能够完整传递，不因接口设计丢失。

### 阶段四：执行端到端验证

实际启动系统，通过 Web UI 发起真实推理并执行到结束。

重点验证包含 Merge 和 Merge-Step 的推理流程。

如果当前测试场景没有触发 Merge 和 Merge-Step，应选用或构造符合现行规范的场景进行验证，不得将未触发视为验证成功。

如果验证过程中发现问题，请继续修改相关实现并重新验证，直到流程满足目标。

### 阶段五：最终一致性检查

检查：

- 最新规范与 Lean 4 代码是否一致。
- Lean 4 与后端接口是否一致。
- 后端数据与 Web UI 展示是否一致。
- Merge 和 Merge-Step 是否真正正确执行。
- 是否仍存在阻止完整推理流程的旧版限制或过时逻辑。

## 八、最终交付要求

完成后请提供简洁但明确的总结，说明：

1. 发现并解决了哪些关键问题。
2. Lean 4、后端、Web UI 分别进行了哪些必要修改。
3. Merge 和 Merge-Step 的实际执行方式，以及如何确认其正确性。
4. 哪些规范文档进行了同步更新。
5. 实际运行的端到端验证结果。
6. 是否仍有未解决的问题。

请区分已经实际验证的行为和仅通过代码检查推断的行为。如果运行环境缺少必要条件，明确说明未验证的部分，不要宣称已经完成端到端验收。

## 九、重要执行原则

- **以完成真实可运行的推理流程为目标，而不是以最小代码改动为目标。**
- 当前有效的规范高于历史实现和旧版限制。
- 允许对阻碍新规范落地的旧代码进行必要重构。
- Lean 4 文档必须始终与实际代码行为保持同步。
- 合适的 Lean 4 工作可以主动交给 OMP，无须每次询问。
- 不能因为 OMP 报告完成，就跳过主 Agent 的检查和集成验证。
- 不得以删除关键推理步骤、放宽语义约束或使用模拟结果的方式掩盖问题。
- 不得将 Merge 和 Merge-Step 的存在等同于它们已被正确使用。
- 遇到问题应继续定位和修复，不要仅生成问题清单就停止工作。

**现在请直接开始执行任务。从现行规范与实际代码的对应关系入手，推进到完整的 Web UI 真实推理验证。最终目标是让系统能够无错误地完成推理，并确认 Merge 和 Merge-Step 按照现行规范正确参与整个推理过程。**
