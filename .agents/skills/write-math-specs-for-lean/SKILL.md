# 文档写作规范

文档的主体是数学定义、推导和证明，同时作为 Lean4 实现与形式化证明的规格。数学读者应能核查结论的依据，实现者应能据此确定类型、函数行为、不变量和待证明命题。

让读者从目录和文件名找到问题，通过链接找到所需细节。项目对象作为例子，不作为所有项目必须采用的模型。

## 先解决疑问，再修改有争议的内容

用户提出疑问时，先回答疑问，再继续相关修改。发现概念重复、语义冲突或归属不明时，及时说明具体问题、影响和建议边界；达成一致后再修改依赖该选择的内容。

解释疑虑要给具体例子。例如讨论当前状态与历史记录时，说明“分支产生两个子节点，后续赋值产生新节点”分别保存什么，以及哪一步可能丢失信息。不要只说“可能不安全”。用户的方案已解决疑虑时，明确接受，并按新边界继续。

已有共识不重复确认。文件排版、措辞调整和链接修复等常规选择，在授权范围内直接完成。文档整理不自动包含语义或代码修改；用户明确授权同步修改时，才处理对应代码。

修改前读取目标项目的权限约束。只读路径只做阅读与讨论，不通过另一个文件、工具或代理绕过限制。本规范不解除目标项目的冻结规则。

## 数学定义、推导和证明是正文主体

补全或改写前，先读该问题依赖的定义、假设与已有命题。保留已经统一的模型，找出真正缺失的定义、推导步骤或证明义务，不为了填满章节新增一套近义对象或未经确认的性质。

定义要足够明确，使不同实现者不必自行补选语义：

- 对象：给出所属集合或类型、构造分量、合法性条件、相等方式和必要不变量。区分对象本身与其解释。
- 函数：给出输入、输出、参数和作用范围。总函数与部分函数明确区分；部分函数写清定义域及无定义的情况。
- 关系与规则：给出成立前提、结果和必要的分支情况。状态转移说明读取旧状态的哪些分量，以及更新和保留哪些分量。
- 假设：显式列出资源有效性、取源齐备、唯一绑定等外部前提。不能将尚未建立的事实隐藏在定义或证明中。

定义、推导、命题和证明各有职责。定义规定对象与规则；推导说明公式如何得到；命题陈述待论证的性质；证明说明结论为什么由前提得到。例子帮助理解，不代替定义或证明。

推导中每个关键等号、等价或蕴含都应有依据：所用定义、已有引理、代数性质或分情况讨论。需要位宽、取模、符号解释或求值条件时，在使用前交代；不能把有条件的等式写成无条件恒等式。

命题写清变量范围、量词、全部假设和准确结论。证明引用具体定义或命题，交代归纳对象、基例、归纳步骤或必要分类。避免用「显然」「由实现可知」省略决定结论的步骤，也不能以结论本身作为证明前提。

无法完成的证明明确列为待证明事项，说明缺少哪个假设、引理或语义对应。不要为凑齐证明临时增加未经讨论的模型假设。

不要求每篇机械地同时包含定义、推导和证明。按该篇的问题选取必要内容；对象定义文件仍不混入操作流程。

## 按问题划分文件，按职责划分目录

每个正文文件回答一个可命名的问题。按内容职责拆分，不按原文件长度平均切分，也不为同一问题建立多个近义文档。

- 对象定义：身份、结构、类型、位宽、值域、相等及必要假设。定义文档不讨论如何操作该对象。
- 对象处理：取值、赋值、比较、读写、覆盖或结果关联。不同处理问题分别成篇。
- 推理步骤：遇到什么情况，作何判断，保留什么结果，失败时如何处理。
- 入口状态：给定环境下的初始条件与初始关系。

例如，“寄存器定义”只维护定义；真实寄存器赋值、虚拟栈读写、Map 关联和包访问放入对应处理文档。Expr 与 Predicate 各有目录；左值、右值、关系符和覆盖策略分别说明。

共同规则按数学对象和问题组织，不因 RV32、eBPF 等架构名称重复分篇。入口条件可以按架构独立成篇；具体行为不同的地方，在对应主题的段落中说明差异。确实无法共享的规则，再说明其独立前提。

## 用准确的中文文件名

中文正文文件使用中文名称，一级标题与文件名一致，省略 `.md`。优先采用“对象＋所讨论的问题”，让读者在打开文件之前知道其职责。

- 定义文件：`寄存器定义.md`。
- 入口文件：`RV32初态描述.md`。
- 处理文件：`比较指令处理.md`、`虚拟栈读写.md`。
- 公式文件：`位向量与共同数值函数.md`。

已有一级标题准确时，优先用它作为文件名。例如“寄存器定义”比“寄存器身份与值域”更能说明整篇的职责；描述初态的文件不称为“入口关系”。避免没有明确范围的“相关说明”“综合分析”等名称。

保留工具或项目要求的标准名称，如 `README.md`、`SKILL.md`。文件重命名仍须符合项目权限与用户授权；命名偏好不覆盖禁止重命名的规则。

## 一个定义只有一个维护位置

定义、公式和详细处理规则在所属正文中维护。其他正文用链接引用，不复制公式，不重新解释同一套处理细节。

一个操作同时涉及多个对象时，按输出职责拆分。例如 helper 的调用身份、参数校验和调用观察属于 Predicate；返回赋值与 Map 关联属于 Expr。两篇相互链接。用户要求把 helper 的 Expr 内容集中在一篇时，保持这一边界，不自行再拆成多个返回主题。

发现两套概念描述了同一问题时，先讨论是否需要两套模型。不能为了迁就现有目录而继续保留重复概念，也不能把删除重复概念当成纯文字调整。

## 推理步骤写判断与处理，细节交给对象文档

节点处理使用独立目录，例如 `NodeInference/`。以推理入口组织阅读顺序，每个处理步骤单独成篇。

步骤正文说明触发条件、判断依据和处理结果。例如检查源项时，说明源齐备则继续、缺失则拒绝，并链接源项取得规则；处理比较指令时，说明方向选择与后继创建，并链接比较 Expr 的定义和覆盖规则。

绝大部分 Expr、Predicate 细节应由对应正文解释。节点文档只补充调度、控制、快照和前后顺序等属于节点处理的问题，不重写值函数、调用契约或关系解释。

## 公式要同时交代符号和适用范围

每组公式附近，用一个简短段落说明新出现的符号：它表示什么、属于什么类型、输入输出是什么、在哪些前提下有定义。不能只列公式，让读者猜测记号。

例如使用 `D_w`、`solve`、`decide` 时，要分别说明部分求值、常量折叠和比较判定的作用，并说明未知或无定义的区别。简单符号在当前段落解释；复杂定义链接到具体正文或小节，不只链接总索引。

注意这些容易混淆的边界：

- 寄存器身份、项位宽、低位视图和访问宽度。
- 完整值绑定、比较约束、观察与历史记录。
- 当前快照与已经产生的历史节点。
- 数学规则、现有实现与尚未实现的范围。

改动基础结构时，同步检查相关公式的类型、成员测试、集合操作、覆盖规则和例子。不能只替换名称，让旧公式继续使用不兼容的对象。

## 让数学规格能够指导 Lean4

数学正文提供确定的语义，具体代码组织与实现进度放在项目指定的工程文档中。实现指导来自精确的定义与命题，不要求数学正文写成代码教程。

从规格到 Lean4，应能建立这些对应：

- 数学对象对应类型及构造方式；合法性条件对应类型约束或显式良构谓词。不要默认数据结构天然保证全部不变量。
- 数学函数对应有明确签名和行为的函数；部分性、拒绝与未知结果有明确表示。无定义不自动变成零、假或空集合。
- 数学规则对应前提检查、分情况处理和结果构造；涉及多目标更新时，明确全部源值来自哪个快照。
- 数学命题对应具有相同量词、假设和结论的 theorem 或 lemma。不能省去假设，也不能用一个更弱命题冒充原结论。

数学集合若以列表表示，要交代重复元素、顺序、键唯一性和相等的处理。数学上的集合相等不自动等于列表结构相等；证明更新代数时，也须说明结论属于哪一种相等。

数学对象与实现表示不同时，明确抽象或解释函数，以及实现需保持的对应关系。例如，对任意满足输入不变量的实现值 x，设 \(\alpha\)、\(\beta\) 分别抽象输入与输出，f 是数学函数，F 是实现函数，y 是成功输出；所需对应可写成

\[
F(x)=\operatorname{success}(y)
\quad\Longrightarrow\quad
\alpha(x)\in\operatorname{dom}(f)
\ \land\ \beta(y)=f(\alpha(x)).
\]

这里 \(\operatorname{success}\) 标记成功结果，\(\operatorname{dom}(f)\) 为 f 的定义域，\(\land\) 表示两个条件同时成立；第二个条件在第一个条件保证 f 有定义时使用。该式仅说明成功结果的可靠性。若还要求完整覆盖数学定义域，就另行陈述成功存在的反向条件；拒绝行为、不变量保持和终止性也按需要分别论证。不能将这些性质合并成一句「实现正确」。

写作前可只读核对已有 Lean4 类型、函数和定理。发现规格与实现不一致时，说明具体差异及其影响，再统一应调整的边界。不能为迎合现有代码而悄悄改写数学定义，也不能声称未实现的规则已有代码支持。

区分三种依据：正文中的数学证明、已有 Lean4 定理及其证明、尚未完成的证明义务。引用已有 Lean4 定理时核对实际命题与假设。编译通过、`#guard` 或有限回归测试不替代一般定理；未完成的形式化证明不能写成已经证明。

## 指令规则说明具体生成什么

指令相关文档要回答“遇到哪类指令，取得哪些源，生成什么关系或观察”。说明立即数与寄存器来源、位宽，以及相等、有符号、无符号和按位判断的差异。

涉及多个架构时，在同一主题中覆盖各架构的相关指令；共同规则集中说明，差异放在具体段落。不能只给一条抽象比较公式，却省略指令到关系的对应。

新增或删除一种关系、角色或观察类型前，先核对已有概念是否已能表达它，以及读者如何区分赋值、条件和历史。模型选择按前述讨论规则达成一致，写作本身不预设答案。

## README 按读者的问题提供入口

总阅读索引使用 `README.md`。除基础阅读顺序外，适合跨目录讨论的问题可有独立入口，下面链接各自负责的正文。

例如“比较问题”链接两篇：Expr 文档解释比较关系，节点文档解释指令处理与后继。README 简短说明二者如何分工，不再加入第三套比较公式。子目录是否需要索引，以读者能否找到内容为准，不机械增加索引层级。

阅读顺序同时反映数学依赖：先基础对象与解释，再局部规则及其性质，随后状态转移和历史性质。命题依赖具体前文或链接，不以文档编号代替依赖说明。

## 写作与收尾

使用克制、准确的中文。先写定义或处理结果，再说明前提、依据与边界。计划使用简短段落或列表，不使用表格。正文结构以问题为准，不强迫每篇套用同一套标题。

数学规格正文聚焦定义、假设、表达式、推导和证明。构建命令、API、FFI、运行诊断和实现状态放在项目指定的工程文档中，不混入数学正文。

完成后从没有参与讨论的读者视角检查：

- 文件名与一级标题是否准确，每篇是否只有一个主要问题。
- 定义和公式是否只维护一处，引用能否到达所需正文。
- 推理步骤是否只解释本步骤的判断与处理。
- 每个新符号是否有解释，相关类型与位宽是否一致。
- 定义域、量词与假设是否完整，推导的关键步骤是否有依据。
- 证明是否实际得到所陈述的结论，证明缺口是否明确标出。
- Lean4 实现者是否能确定类型、函数签名、失败行为和需保持的不变量。
- 数学与实现表示的对应是否明确，形式化证明与测试是否如实区分。
- 旧术语、旧文件名和已删除概念是否仍出现在正文或链接中。
- 例子是否符合最终达成的语义边界。

交付时明确实际完成的文档、改动范围、检查结果和未解决问题。代码未修改时不要说代码已同步，检查失败时不要说全部通过，也不要让用户猜测工作是尚未开始还是已经完成。
